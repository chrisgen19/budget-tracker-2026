# Receipts

## Key Patterns

- **Receipt scanning** is opt-in per user — toggled in Profile Settings > Features; uses Gemini AI for OCR and per-category itemization
- **Receipt year repair** (`src/lib/receipt-date.ts`): `checkReceiptDate` normally warns about a suspicious year without touching it, but overrides one readable case — when the OCR year disagrees with the photo's while the month and day match it *exactly*. That signature is a misread digit, not an old receipt, since reading a different date wrong almost never lands on the photo's month and day; it was seen in production as `08/26/2026` read back as `2023-08-26`. A repair always sets `dateWarning` and reports `repairedFromYear`, which the review renders as "year corrected from 2023" and `scan_receipt` states in prose, because an inference the user cannot see is one they cannot undo. Deliberately narrow: "same month" or "within a few days" would start rewriting dates that were read correctly. Note this is the one place a *readable* receipt date is influenced by the photo date, narrowing the rule below
- **Photo capture dates** (`src/lib/exif-date.ts`): `readPhotoTakenAt` pulls EXIF `DateTimeOriginal` out of JPEG/HEIC bytes with no dependency, since the tag is fixed-width ASCII inside a standard TIFF block that both formats embed. The Telegram bot has no `File.lastModified` to read, so an unreadable receipt date used to fall back to *today*, putting a receipt photographed days earlier on the day it was uploaded. EXIF timestamps carry no timezone by specification, which is exactly the offset-less shape `resolveTransactionDate` wants; appending a `Z` would claim UTC. It survives only when the image is sent as a **file**, since Telegram re-encodes photos and strips metadata. Used whole rather than as a bare date, so the timestamp is real and label schedules can run against it instead of an invented clock
- **Receipt captions** — free text sent with a photo reaches `scanReceipt` as a `caption` and is quoted into the prompt as a *hint*, capped at `MAX_CAPTION_CHARS`. Deliberately not applied afterwards as a description override: "here you go" is an ordinary thing to send with a photo, and pasting it over a correctly-read merchant name is worse than ignoring it, whereas the model can weigh it against what it reads. It is also the only route by which the caption can reach `categoryId`, which is the field OCR most often gets wrong and which a post-hoc description swap could never help. The receipt wins on conflict, and the prompt tells the model to read `amount` and `date` from the image alone. That is a steer, not a guarantee — prose cannot bind a model, and a caption naming a figure could in principle be echoed into `amount`. What actually protects those two fields is the confirmation step, which receipt scanning has always required for precisely this reason: OCR on a crumpled phone photo is where a wrong amount comes from, so nothing is written until the user has seen it. The caption sits *below* the category rules and above only the response format, so it cannot appear to re-scope the rules it must not override. The Telegram review says "I used your caption as a hint" when one was sent, on the same principle as the repaired receipt year: an inference the user cannot see is one they cannot undo. "The receipt wins" is scoped to what the receipt actually *prints* — the amount, the date, and a merchant it names. A wallet transfer prints an account holder and a reference number and nothing about the purchase, so there the caption is the only description that exists and the user's own wording is kept, place names the image cannot corroborate included: `Tiendesitas Yosh's Pickleball fee` came back as `Yosh's Pickleball fee`, which is a row nobody can place a month later. The prompt also says an instruction inside a caption ("category fun") is not description text and that removing one must not take the purchase with it

- **Receipt scan quota** (`src/lib/scan-quota.ts`) — a credit is reserved *before* the Gemini call and settled after: `SUCCESS` spends it, `FAILED` refunds it, so users are never charged for a scan they can't use. Reservations serialise per user with a Postgres advisory lock (a bare count-then-insert cannot enforce a limit under READ COMMITTED). Because refunds mean the monthly limit no longer bounds API spend, a rolling attempt rate limit does. `FAILED` rows are kept, not deleted, so refunded attempts still count toward it
- **Receipt itemization** — multi-scan groups transactions by `receiptGroupId`; per-transaction `receiptBreakdown` JSON stores individual line items for each category

## Receipt photos

- **Storage** (`src/lib/receipt-photo-storage.ts`): a private Cloudflare R2 bucket over the S3 API, signed with `aws4fetch`. All four `R2_*` variables or none: any blank one disables photos, the routes answer **503** `PHOTOS_DISABLED` and no attach UI renders. The object key is `receipts/{userId}/{photoId}.jpg` and is never built from a description or an amount, since a bucket listing must not read like a ledger. `put`, `get`, `delete` (a 404 counts as deleted) and `list(prefix)`, a ListObjectsV2 walk that follows continuation tokens and returns each key with its `lastModified`, used only by the prune script. The XML is parsed with regexes, since Node has no DOM parser and the shape is fixed; a page that claims to be truncated with no token is an error rather than a loop. Requests are signed with `client.sign()` and then sent as `fetch(signed.url, { headers: signed.headers, body })` with the **original** bytes, never as `fetch(signedRequest)`: Next's patched server `fetch` rebuilds a `Request` input from its body stream, which has no length, so the PUT goes out chunked and R2 answers **411**. The unit tests stub `fetch`, so they can pin the call shape but only a real server talking to R2 shows the failure
- **Re-encoded, metadata stripped** (`src/lib/receipt-photo-image.ts`): every photo is decoded and re-encoded by `sharp` as a JPEG at quality 80, upright, longest side at most `MAX_IMAGE_DIMENSION` (1500) and never enlarged. Metadata is stripped **by omission**: `sharp` keeps EXIF, ICC and XMP only when `withMetadata` is called, so nothing here may call it. That is what keeps a phone's GPS position out of the bucket. Undecodable bytes throw `UnreadableImageError` (422 on the route). HEIC is the exception: the installed `sharp` build decodes HEIF for AVIF only, so a HEIC upload the browser could not convert to JPEG always fails to decode and is answered **415** (and refused by `attach_receipt_photo` as `UNSUPPORTED_HEIC`); the form and the scan save therefore refuse or skip a still-HEIC image client-side with a toast (`src/lib/heic.ts`). `scripts/verify-receipt-photos.ts` uploads a JPEG carrying GPS EXIF and asserts the served bytes carry none
- **Upload first, link at save** (`storeReceiptPhoto` in `src/lib/receipt-photos.ts`): `POST /api/receipt-photos` stores the photo and returns its id; the transaction write then names it as `receiptPhotoId`. The form keeps a chosen photo as a local `File` and uploads it at submit, so a photo is never stored for a form that was abandoned. Idempotent on `(userId, photoKey)`: a retry returns the stored photo with `replayed: true` and writes nothing to R2. The id is generated before the PUT and passed to the row insert, so the object and the row share it; object first, row second, so a row never points at nothing. An insert Postgres refused deletes the object again; one whose outcome is unknown (a connection dropped after the commit) keeps it, since a committed row may name it, and an object with no row is the prune's. A failed upload still saves the transaction, with the toast `Saved. The photo didn't upload: attach it from the transaction.` The form waits for a photo still compressing before it uploads, discards a compression a later choose or remove superseded, disables the photo controls while the save runs, and skips the write when Cancel is pressed or the form closes during the upload. Upload bodies are metered by `readUploadForm`, not just checked against `content-length`
- **Linking** (`src/lib/receipt-photo-links.ts`, database only so the shared create path never loads sharp or R2): `photosAreOwned` checks ownership inside the write transaction under `FOR KEY SHARE`, and another user's photo and a missing one get the same refusal. `applyPhotoChange` is the one edit rule: a **replace** moves every row that shared the old photo, since the rows of one split receipt are one purchase, under `FOR UPDATE` on those rows ordered by id as its first statement; a **remove** unlinks only that row; a **link** attaches only that row. It stamps the rows it moves, `APP` by default, or the token's source and id when the MCP tool calls it. The edit route goes through `changePhotoUnderLock`, which locks the edited row and reads its photo under that lock before deciding: a photo read before the transaction opened let a concurrent replace leave one split receipt on two photos. Bulk delete reads the photo links of the rows it deletes under `FOR UPDATE` too, so cleanup is told the photo each row held when it went. The multi-scan save uploads any photo still missing an id on every attempt, including a pinned retry, and says a photo is missing from the rows the server returned rather than from the uploads, since a replay keeps the first attempt's links
- **Cleanup and its locking** (`deleteUnreferencedPhotos`): runs only after the unlinking write commits, and deletes the **row first**, through a guarded `deleteMany`, then the object only when that row really went. Each row delete takes `FOR UPDATE` on the photo as a **separate first statement**. A writer that has just inserted a transaction on the photo holds `FOR KEY SHARE` through the foreign key until it commits, so the lock waits, and the `deleteMany` then runs on a fresh READ COMMITTED snapshot that sees the new link and deletes nothing. A single `DELETE ... WHERE NOT EXISTS` would also wait, but then proceeds on its stale snapshot and the `SET NULL` wipes the link that just committed. `scripts/verify-receipt-photos.ts` proves this on two real connections and fails with the lock removed. `cleanUpReceiptPhotos` wraps it for the routes and never throws, so a storage failure cannot fail a write that already succeeded; it leaves the orphan for the prune script
- **Telegram and MCP**: the bot keeps the photo's base64 on its pending scan and, only after a save that landed, calls the MCP tool `attach_receipt_photo` with the created ids and the save's own batch key as `photoKey`, so a redelivered "yes" replays the stored photo. A failure appends `The photo didn't upload: attach it from the app.` and never fails the save; a server with no R2 says nothing at all. See `mcp.md` and `telegram.md`
- **Prune script** (`scripts/prune-orphan-receipt-photos.ts`): the backstop for what cleanup cannot reach: rows no transaction references and objects under `receipts/` with no row (a `storage.delete` failing after its row was deleted leaves exactly that). Only rows and objects older than **24 hours** are touched, since a photo is uploaded before the transaction that links it is saved. Rows go through `deleteUnreferencedPhotos`, so each is re-checked under its lock. Dry run by default, `--apply` deletes, and `--apply` refuses without R2, since deleting a row without its object creates the orphan being removed. Refuses a non-local `DATABASE_URL` unless `--allow-remote` is passed: production pruning is run deliberately, by hand. **Running the prune in production:** it is never run automatically (no cron, not part of a deploy). `tsx` may be absent from the standalone image and the container's `DATABASE_URL` points at a non-local service host, so run it from a local checkout with the production `DATABASE_URL` and the four `R2_*` values in the environment: a dry run first, then `pnpm exec tsx scripts/prune-orphan-receipt-photos.ts --allow-remote --apply`. R2 request timeouts are 10 seconds each (`STORAGE_TIMEOUT_MS`), so a hung bucket fails a call rather than stalling it
